# 開発フロー

AI エージェントと進める開発の手順です。CLAUDE.md には要点だけを置き、詳細はここに書きます。
元になったのは、Claude プロジェクト「開発方法」で作った開発フロー見直し案です。

## 全体の流れ

| # | ステップ | 担当 | やること |
|---|---|---|---|
| 1 | 依頼 | ユーザー | 「目的」「背景」「完了条件」「やらないこと」の4項目で書く |
| 2 | 計画 | 実装スレッド | CLAUDE.md と過去の指摘メモ（関係する行だけ）を読む。大きめの作業は計画をチェックリストで示す |
| 3 | 実装 | 実装スレッド | ブランチを切る。広い調査はサブエージェントに任せ、要約だけ受け取る |
| 4 | 自己検証 | 自動（Hooks） | lint・型チェック・テストを実行。通るまで完了しない |
| 5 | PR と CI | 実装スレッド | テンプレートに沿って PR を出し、CI が落ちたら自分で直す。動作が変わる PR は `verify-flow` スキルで実画面を検証し、見た目が変わる PR は画面のスクリーンショットを付ける |
| 6 | AI レビュー | 別スレッド | `pr-review` スキルで、根拠付きの指摘と判定を出す |
| 7 | 修正ループと最終確認 | 実装スレッド → ユーザー | 「必須」がなくなるまで修正と再レビュー。3周で終わらなければユーザーに判断を仰ぐ。終わったらユーザーが確認してマージ |
| 8 | 学びの記録と定期整理 | 実装スレッド / 週1の定期実行 | 合格後、同じ PR で指摘メモに追記。週1回、検証・昇格・削除の PR を出す |

ユーザーが手を動かすのは、1 の依頼、7 の最終確認、8 の整理 PR の承認だけです。

## 1. 依頼の型

```markdown
- 目的: 何のためにやるか
- 背景: 今どうなっていて、何が困っているか
- 完了条件: 何ができたら終わりか（確かめ方も）
- やらないこと: 今回は触らない範囲
```

完了条件が書かれていない、または確かめようがない依頼は、エージェントが着手前に質問して埋めます。
Issue で依頼するときは `.github/ISSUE_TEMPLATE/request.md` を使います。

## 4. 自己検証（Hooks）

`.claude/settings.json` の Stop フックが `.claude/hooks/verify.sh` を実行します。

- `package.json` にある `lint`・`typecheck`・`test` スクリプトだけを実行します（無いもの、`npm init` 既定の `test` は飛ばします）。
- 未コミット・未プッシュの変更がないとき、または変更が Markdown と `docs/` だけのときは何もしません。
- 失敗したときだけ、失敗したコマンドと出力の末尾30行を返し、作業の完了を止めます。
- 同じ停止で2回目に呼ばれたときは、無限ループを避けるため通します。その場合は完了とせず、PR の「検証結果」に失敗を正直に書いてユーザーに伝えます。

## 5. PR と画面の確認

見た目が変わる PR（`src/`・`scripts/build.mjs` の変更）は、変更したページを実際に表示して確かめ、スクリーンショットを PR に付けます。

1. 別のターミナルで `npm run dev` を起動する（http://localhost:8788）。
2. `npm run screenshot -- --pr <PR番号> <変更したページのパス…>` を実行する（例: `/ /es/ /pt/historia/`）。
   ローカルの Chrome のヘッドレスモードで、デスクトップ（幅1280）とスマホ（幅500）を撮ります。
   高さは既定で2200px で、それより下は撮れません。経歴ページのような長いページは `--height 6000` などを付けます。
3. 画像は `screenshots` ブランチの `pr-<番号>/` に置かれ、PR に貼る Markdown の表が出力されるので、PR の「画面の確認」に貼る。
4. 撮った画像は自分でも見て、崩れや表示されない部分がないか確かめる。英語・スペイン語・ポルトガル語のうち、変更したものはすべて撮る。

見た目が変わらない PR は「画面の確認」に「なし（見た目の変更なし）」と書きます。

### 実画面での検証

ボタン・メニュー・言語の提案・動画など、操作で動きが変わる PR は、`.claude/skills/verify-flow/` の手順で
`npm run verify` を実行し、PASS・FAIL・BLOCKED と出力を PR の「検証結果」に貼ります。
フローは `test/flows/*.json` にあり、変更した動作のフローがなければ同じ PR で足します。
BLOCKED（サーバーや Chrome がない、開いたページが存在しない）は検証できていないということなので、完了としません。

Chrome を動かすので CI では実行せず、PR ごとに実装スレッドが実行します。

## 6. AI レビュー

- 実装したスレッドとは**別のスレッド**で行います。実装の経緯を知らない状態で差分を見るためです。
- 指示は `.claude/skills/pr-review/SKILL.md` に固定しています。観点はバグ・セキュリティ・設計の3つ。
- 指摘には `ファイル:行` と具体的な失敗を書き、重大度（必須・推奨・任意）と最後に判定（合格・要修正）を付けます。

## 7. 修正ループ

1. 実装スレッドは「必須」の指摘をすべて直し、「推奨」は直すか、直さない理由を PR に書きます。
2. 直したら、レビューのスレッドで再レビューします。
3. 判定が「合格」になったら、ユーザーに最終確認を依頼します。
4. **3周しても「合格」にならなければ**、残っている指摘と論点をまとめてユーザーに判断を仰ぎます。

## 8. 学びの記録と定期整理

レビューが「合格」になったら、最終確認を依頼する前に、実装スレッドが `docs/review-lessons.md` の3つの見出しに1行ずつ追記し、同じ PR にコミットします。
マージ後に別の PR を作らないので、追記が main に入らないまま残ることがありません。

- **指摘**: レビューで出た指摘
- **うまくいった手順**: 例「先に型を定義してから実装すると手戻りがなかった」
- **環境の事実**: 例「このテストは遅いので単体で回す」

週1回、定期実行のジョブが次を行い、差分を PR で出します（この PR も同じフローを通ります）。

1. 繰り返された指摘や手順を、CLAUDE.md かレビュー用スキルに昇格させ、メモからは消す。
   コードを見て機械的に確かめられる決まりは、文書ではなく `test/rules.test.mjs` のチェックにする（CI で落ちるので忘れられない）。
2. 古くなった行、反映済みの行を消す（メモは50行以内が目安）。
3. 記憶が今も正しいかを検証する。CLAUDE.md のコマンドを実際に実行し、書かれたファイルや関数が存在するか確かめる。
4. 合わなくなった行は直すか削除し、残した行の「検証」の日付を更新する。

PR が3〜5件たまってから始めます。

## コンテキストとコストの扱い

| 問題 | 対策 |
|---|---|
| CLAUDE.md が肥大化する | 100行以内。手順や詳細は docs/ と Skills に移し、必要なときだけ読ませる |
| レビューの指示が常に載る | レビュー用スキルにし、レビューのスレッドでだけ読ませる |
| テストや lint の結果が会話を埋める | Hooks で実行し、失敗したときだけ要点を返す |
| 広い調査で会話が膨らむ | サブエージェントに任せて要約だけ受け取る。1依頼に1スレッド |
| ツール定義が常にトークンを使う | MCP サーバー・サブエージェント・スキルは、このリポジトリで使うものだけ登録する |
| 指摘メモが肥大化する | 計画時は関係する行だけ検索して読む。週1の整理で消す |
| 先頭部分が変わるとキャッシュが効かない | CLAUDE.md や設定は作業中に編集せず、週1の整理 PR にまとめる。日付など毎回変わる値を書かない |
| 途中でコンテキストを入れ替えると高くつく | セッションの途中でツールやスキルの構成を変えない。別の作業は新しいスレッドで |
