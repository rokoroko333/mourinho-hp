# 設計判断スキルの評価

`.claude/skills/design-debate/SKILL.md` を変える PR では、答えの分かっている過去の機能の計画でディベートをやり直し、
着手前に見つけられた論点を見落とすようになっていないかを確かめます。レビュー用スキルの評価（`docs/skill-evals.md`）の設計判断版です。

## 評価ケース

| ケース | 渡すもの | 正解リスト |
|---|---|---|
| #62 ファン予想 | `docs/plans/phase3.md` の「2. ファン予想」の節と、CLAUDE.md の「目的と読者」「サイトのルール」 | 下の G1〜G13 |

#62 の正解リスト（#62 の PR 本文と AI レビュー6件で実際に出た論点）:

| # | 論点 |
|---|---|
| G1 | 票の書き込みと集計の更新が別々で、片方だけ失敗すると食い違う（1周目の必須） |
| G2 | IPv6 は /64 に丸めないと、アドレスを変えて1接続1票と連投の上限をすり抜けられる |
| G3 | 接続元のヘッダー（`CF-Connecting-IP`）がないと、全員が1つの接続にまとまる |
| G4 | IPv4 射影アドレス（`::ffff:a.b.c.d`）の扱い |
| G5 | 重複した送信が連投の回数に入る（判定の順序） |
| G6 | 検証フローが本番に票を入れない、フォームがないと空振りで PASS する |
| G7 | 同じ回線（家庭・会社の Wi-Fi、携帯の回線）の2人目が投票できない |
| G8 | デプロイの順番（マイグレーション → 秘密の値 → Worker → Pages） |
| G9 | 移籍で `TEAM_ID` が変わったときの、進行中の投票 |
| G10 | 延期・時刻の変更。締め切りはサーバー側で判定する |
| G11 | 集計は投票した後に見せる。票が少ないうちは割合を出さない |
| G12 | IP を保存せず、試合ごとに別の値になる鍵付きハッシュで重複だけ判定する |
| G13 | 入力の範囲と、別サイトからの送信（Origin）の検査 |

オーナーが実際に決めた3点（スパム対策は外部サービスなしで自前、個々の票は30日で消して集計だけ残す、集計の見せ方）が「オーナーが決めること」に入っているかも見ます。

## 進め方

1. 別のスレッド（またはサブエージェント）で実行する。このファイルと `docs/review-lessons.md`、#62 以降のコード・PR・git の履歴には答えがあるので、見せない。
   渡すのは上の「渡すもの」の文章とスキルだけにし、ファイルやリポジトリを読ませない。
2. 正解リストの1項目ごとに、着手前に挙げていれば1点、半分なら0.5点（13点満点）。
3. 変更前のスキルでも同じように実行して比べ、点数の表を PR の「検証結果」に貼る。1回ずつの結果はぶれるので、下がったら再実行して確かめる。

## これまでの結果

| 日付 | 型 | 点数 | 決めること3点 |
|---|---|---|---|
| 2026-10-31 | 3人ディベート（スキルの元になった型） | 5.5 | 3点とも |
| 2026-10-31 | 比較: 1人に「この計画についてどう思いますか？」 | 4 | 3点とも |
| 2026-10-31 | 比較: 会議ログ型（見落としている前提3つ＋その場にいない立場から反論1つ） | 3 | 1点 |

どの型も G2〜G8（実装の細部）は0点でした。これらは PR のレビューで見つけるもので、このスキルで点を取りにいく必要はありません。
採点は正解を知っている者がしたので、甘くなっている可能性があります。

## ケースの足し方

着手前に「オーナーと決めること」があった機能の PR がマージされたら、その計画と、PR とレビューで出た論点を1行足せます。
例: 第3段階の「3. 記録トラッカー」（2026-10-31 のディベートで、ESPN の結果が今季分だけでシーズンが替わると数字が減る、という指摘が出た）。
