# 設計判断のディベート

1人の AI に「どう思う？」と聞くと、聞き手に合わせた無難な答えが返ります。
専門と性格の違う3人に議論させると論点が割れ、割れた所にだけ「オーナーが決めること」が現れます。
あなたは3人を演じ分け、最後に審判役のオーナーへ判断材料を渡します。**結論は出しません。**

使う場面は、作り方より前の「何を作るか、どう作るか」です。PR のレビュー（`pr-review`）の代わりにはなりません。
#62 の計画で試したとき、保存の仕方や見せ方は着手前に当たりましたが、IPv6 の丸めやデプロイの順番などの実装の細部は1つも当たりませんでした（`docs/design-evals.md`）。

## 使わない場面

- 決めることがない作業（文言の修正、既存の型どおりのページ追加、バグ修正）。
- オーナーがすでに方式を決めている作業。決まったことを蒸し返さない。

## 進め方

1. 課題を1文に絞る。「ファン予想をどう作るか」ではなく、「投票の重複をどう防ぎ、何日残し、集計をいつ誰に見せるか」まで具体にする。
   抽象的なままだと3人が並んで一般論を言うだけになります。
2. 下の対立軸から、課題に一番効く2つを選び、3人を立てる。2人は軸の両端、3人目は「オーナー1人で回せるか」を問う運用とコストの役にする。
   性格も書く（強気の拡大派、石橋を叩く慎重派、現実派）。仲良く済む組み合わせにしない。
3. 3往復ほど議論させる。CLAUDE.md・`docs/`・コードは読んでよい。
4. 丸く収まりかけたら角度を変える。「直前の意見に、ほかの2人はそれぞれ賛成か反対かを明言し、さっきまでと違う角度から自分の専門で反論する。同じ論点を繰り返さず、新しい論点を必ず1つ足す」。1回でよい。
5. 合意できるところまで続け、合意できない点は揉めたまま残す。
6. コードやデータについての主張（「ESPN の結果は今季分だけ」など）は、出力の前にコードで確かめる。確かめられなければ「（要確認）」を付ける。
7. 下の形式でオーナーに出す。オーナーが決めたら、決まったことを計画（`docs/plans/`）か依頼の「聞かずに変えてはいけないもの」に書いてから実装に入る。

## mourinho-hp の対立軸

| 軸 | 一方 | もう一方 |
|---|---|---|
| 流入と負荷 | 流入・SEO（4言語、hreflang、シェア） | 表示速度と Cloudflare 無料枠（1日15,000訪問、Functions・KV・D1 の上限） |
| 事実と鮮度 | 事実の正確さ（出典と時点が必須） | 更新の速さと盛り上がり（試合の翌日に数字が動く） |
| 体験と守り | ファン体験（投票、シェア、目立つ配置） | セキュリティとプライバシー（個人情報を持たない、不正、外部 SDK なし） |

運用とコストの役は毎回入れます。見るのは、壊れたとき誰が直すか、移籍や延期など将来の変化、無料枠の上限です。

## 出力形式

ディベート本文のあとに、次の3つを必ず付けます。オーナーが読むのは主に3つ目です。

```markdown
## 3人が合意できたこと
- 投票 API は1文の書き込みだけにし、集計は別に数える（片方だけ失敗して食い違うのを防ぐ）

## まだ揉めている論点
- 個々の票を残す期間: B は7日（用が済めば消す）、C は30日（スコアの訂正に気づくまでの猶予）

## オーナーが決めること
| 決めること | 選択肢 | 推奨と理由 |
|---|---|---|
| 個々の票を残す期間 | 7日 / 30日 | 30日。1人の運用で訂正に気づくまでの猶予が要る。集計だけは残す |
```

- 「合意できたこと」に入ったものは、オーナーがもう悩まなくてよいものです。本当に3人とも賛成したものだけを入れる。
- 「オーナーが決めること」には必ず推奨を1つ付ける。推奨がオーナーの判断を代わりにするわけではありません。
