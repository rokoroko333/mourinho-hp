# 開発フロー

AI エージェントと進める開発の手順です。CLAUDE.md には要点だけを置き、詳細はここに書きます。
元になったのは、Claude プロジェクト「開発方法」で作った開発フロー見直し案です。

## 全体の流れ

| # | ステップ | 担当 | やること |
|---|---|---|---|
| 1 | 依頼 | ユーザー | 「目的」「背景」「完了条件」「やらないこと」「聞かずに変えてはいけないもの」の5項目で書く |
| 2 | 計画 | 実装スレッド | CLAUDE.md と過去の指摘メモ（関係する行だけ）を読み、機能マップで変える場所と検証フローを探す。大きめの作業は計画をチェックリストで示す |
| 3 | 実装 | 実装スレッド | ブランチを切る。広い調査はサブエージェントに任せ、要約だけ受け取る |
| 4 | 自己検証 | 自動（Hooks） | lint・型チェック・テストを実行。通るまで完了しない |
| 5 | PR と CI | 実装スレッド | テンプレートに沿って PR を出し、CI が落ちたら自分で直す。動作が変わる PR は `verify-flow` スキルで実画面を検証し、見た目が変わる PR は画面のスクリーンショットを付ける |
| 6 | AI レビュー | 別スレッド（クラウドのルーティン） | `pr-review` スキルで、差し戻す理由を探す立場から根拠付きの指摘と判定を出す |
| 7 | 修正ループと最終確認 | 実装スレッド → ユーザー | 「必須」がなくなるまで修正と再レビュー。3周で終わらなければユーザーに判断を仰ぐ。終わったらユーザーが確認してマージ |
| 8 | 学びの記録と定期整理 | 実装スレッド / 週1のルーティン | 合格後、同じ PR で指摘メモに追記。週1回、PR が3件以上たまっていれば、検証・昇格・削除の PR を出す |

ユーザーが手を動かすのは、1 の依頼、7 の最終確認、8 の整理 PR の承認だけです。

## 1. 依頼の型

```markdown
- 目的: 何のためにやるか
- 背景: 今どうなっていて、何が困っているか
- 完了条件: 何ができたら終わりか（確かめ方も）
- やらないこと: 今回は触らない範囲
- 聞かずに変えてはいけないもの: 触る可能性はあるが、変える前に必ず確認してほしいもの（なければ「なし」）
```

「やらないこと」は触らない範囲、「聞かずに変えてはいけないもの」は触るなら先に確認が要るものです
（例: CSP・`_headers`、デプロイ設定、テストの削除や緩和）。
エージェントは PR の「聞かずに変えてはいけないもの」欄に依頼の内容を写します。これに当たる変更が必要になったら、
手を付ける前にユーザーに確認し、了承（いつ、どこで、何を）を同じ欄に書きます。

完了条件が書かれていない、または確かめようがない依頼は、エージェントが着手前に質問して埋めます。
Issue で依頼するときは `.github/ISSUE_TEMPLATE/request.md` を使います。

## 4. 自己検証（Hooks）

`.claude/settings.json` の Stop フックが `.claude/hooks/verify.sh` を実行します。

- `package.json` にある `lint`・`typecheck`・`test` スクリプトだけを実行します（無いもの、`npm init` 既定の `test` は飛ばします）。
- 未コミット・未プッシュの変更がないとき、または変更が Markdown と `docs/` だけのときは何もしません。
- 失敗したときだけ、失敗したコマンドと出力の末尾30行を返し、作業の完了を止めます。
- 同じ停止で2回目に呼ばれたときは、無限ループを避けるため通します。通ったあとも失敗が残っていれば、完了とせず、
  失敗をそのまま PR の「検証結果」に書いてユーザーに伝えます（ここが正本。CLAUDE.md は要点だけ）。

## 5. PR と画面の確認

見た目が変わる PR（`src/`・`scripts/build.mjs` の変更）は、変更したページを実際に表示して確かめ、スクリーンショットを PR に付けます。

1. 別のターミナルで `npm run dev` を起動する（http://localhost:8788）。
2. `npm run screenshot -- --pr <PR番号> <変更したページのパス…>` を実行する（例: `/ /es/ /pt/historia/ /ja/history/`）。
   パスを渡さないと、4言語のトップ（`/ /es/ /pt/ /ja/`）を撮ります。
   ローカルの Chrome のヘッドレスモードで、デスクトップ（幅1280）とスマホ（幅500）を撮ります。
   高さは既定で2200px で、それより下は撮れません。経歴ページのような長いページは `--height 6000` などを付けます。
3. 画像は `screenshots` ブランチの `pr-<番号>/` に置かれ、PR に貼る Markdown の表が出力されるので、PR の「画面の確認」に貼る。
4. 撮った画像は自分でも見て、崩れや表示されない部分がないか確かめる。4言語のうち、変更したものはすべて撮る。
   スマホの実寸（375・320px）は、ヘッドレス Chrome が幅500px未満を撮れないので、`npm run verify`（画面の大きさを指定できる）で確かめる。

見た目が変わらない PR は「画面の確認」に「なし（見た目の変更なし）」と書きます。

### 実画面での検証

ボタン・メニュー・言語の提案・動画・予想など、操作で動きが変わる PR は、`.claude/skills/verify-flow/` の手順で
`npm run verify` を実行します。手順・フローの書き方・PASS／FAIL／BLOCKED の扱いは、そのスキルが正本です。
Chrome を動かすので CI では実行せず、PR ごとに実装スレッドが実行します。

## 6. AI レビュー

- 実装したスレッドとは**別のスレッド**で行います。実装の経緯を知らない状態で差分を見るためで、
  書いた者に自分の変更を承認させないためでもあります（同じモデルでもスレッドを分けます）。
- レビュアーの役割・観点・重大度・出力形式は `.claude/skills/pr-review/SKILL.md` だけに書きます。ここには写しません。
- 判定は「合格」か「要修正」の二択です。「要修正」なら 7 の修正ループを回します。
- 手段は、クラウドのルーティン「mourinho-hp: PR の AI レビュー」です（下の「ルーティン一覧」）。
  実装スレッドが自分のサブエージェントでレビューを済ませることはしません（`docs/skill-evals.md` の評価のときだけ使います）。
- PR 本文を書き終えてから起動します（空の本文をレビューされないように）。コミットを足したら、そのたびに起動し直します。
- 1つのコミットに2件のコメントが付くことが多いので、`<!-- ai-review:SHA -->` の付いたコメントが2件そろうまで待ち
  （最長20分。1件しか付かなければその1件で進め、PR にそう書く）、全部を読んで推奨を拾います。

## 7. 修正ループ

1. 実装スレッドは「必須」の指摘をすべて直し、「推奨」は直すか、直さない理由を PR に書きます。
2. 直したら、レビューのスレッドで再レビューします。
3. 判定が「合格」になったら、ユーザーに最終確認を依頼します。
4. **3周しても「合格」にならなければ**、残っている指摘と論点をまとめてユーザーに判断を仰ぎます。

## 8. 学びの記録と定期整理

レビューが「合格」になったら、最終確認を依頼する前に、実装スレッドが `docs/review-lessons.md` の3つの見出しに1行ずつ追記し、同じ PR にコミットします。
マージ後に別の PR を作らないので、追記が main に入らないまま残ることがありません。

- **指摘**: レビューで出た指摘
- **うまくいった手順**: 例「先に型を定義してから実装すると手戻りがなかった」
- **環境の事実**: 例「このテストは遅いので単体で回す」

週1回（月曜）、前回の整理から PR が3件以上たまっていれば、ルーティン「mourinho-hp: 週1の整理」（下の「ルーティン一覧」）か、
ユーザーに頼まれた実装スレッドが次を行い、差分を PR で出します
（この PR も同じフローを通ります。マージの前にユーザーの承認を受けます。3件未満の週は見送ります）。

1. 繰り返された指摘や手順を、下の「強制力の段」のできるだけ上の段に昇格させ、メモからは消す。
   レビューで「（テスト化候補）」が付いた指摘は、繰り返しを待たずに `test/rules.test.mjs` のチェックにする。
2. 古くなった行、反映済みの行を消す（メモの項目は50行以内が目安。ここが正本）。
3. 記憶が今も正しいかを検証する。CLAUDE.md のコマンドを実際に実行し、書かれたファイルや関数が存在するか確かめる。
4. 合わなくなった行は直すか削除する。「検証」の日付は、実際に確かめた行だけ更新する。

### 強制力の段

同じことを伝えるにも、エージェントが無視できない順に段があります。昇格させるときは、できるだけ上の段を選びます。

| 段 | 手段 | 向いているもの |
|---|---|---|
| 1 | 作り（`scripts/build.mjs` の関数・データの形） | 間違った書き方がそもそもできない形にできるもの。例: タイトルのカードを `trophyCard` 関数にまとめ、どのページでも出典が一緒に出る（#33） |
| 2 | テストと CI（`test/rules.test.mjs`・`test/build.test.mjs`） | コードを見て機械的に確かめられる決まり。わざと違反させて落ちることを確かめる |
| 3 | CLAUDE.md・スキル | 判断が要る決まりや手順。読み飛ばされることがある |
| 4 | 指摘メモ（`docs/review-lessons.md`） | まだ1回しか出ていない学び。週1回の整理で上の段に移すか消す |
| 5 | 人のレビュー | 上の段で防げなかったものを見つける場所。同じ指摘を繰り返すなら、上の段に移す合図 |

ルーティンの指示文は claude.ai 側にあり、リポジトリのテストでは確かめられません。整理のたびに、名前・ID・時刻と指示文の前提（言語の数など）を
claude.ai 側（RemoteTrigger の `list`）と突き合わせ、ずれていればこの表かルーティンを直します。レビューのルーティンは `.claude/skills/pr-review/SKILL.md` を読んでその指示に従うので、
レビューの観点を変えるときはスキルを変えます（下の「スキルを変えるとき」）。

## スキルを変えるとき

レビュー用スキル（`.claude/skills/pr-review/`）を変える PR では、`docs/skill-evals.md` の評価ケース（過去の PR で見つかった問題）を、
変更前と変更後のスキルで別々にレビューして点数を比べ、表を PR に貼ります。
文面の改善で、以前は見つけられた問題を見落とすようになっていないかを確かめるためです。

## 決まりを書く場所（正本）

同じ決まりを2か所に書くと、片方だけ直って食い違います（#1）。決まりごとに正本を1つ決め、ほかの場所からはリンクで指すだけにします。
直すときは、写しが残っていないか `grep` で探します。

| 決まり | 正本 |
|---|---|
| 毎回守るリポジトリ固有の約束・落とし穴と、作業の流れの要点 | `CLAUDE.md` |
| フローの各ステップの詳細と理由 | このファイル |
| レビューの役割・観点・重大度・出力形式 | `.claude/skills/pr-review/SKILL.md` |
| 実画面での検証の手順 | `.claude/skills/verify-flow/SKILL.md` |
| ページ・要素・検証フローの対応 | `docs/feature-map.md` |
| 機械的に確かめられる決まり | `test/rules.test.mjs`・`test/build.test.mjs` |
| まだ1回しか出ていない学び | `docs/review-lessons.md` |

## CLAUDE.md を変えるとき

CLAUDE.md の約束や作業の流れを削る・書き換える PR では、`docs/context-evals.md` の代表タスクで、
変更前と変更後の CLAUDE.md の計画を比べ、表を PR に貼ります。削ったせいで、見ても分からない約束を落とすようになっていないかを確かめるためです。
削ったことで問題が出ても、すぐ元の長文に戻さず、起きた失敗だけを防ぐ最小限を足します（できればテストで）。

## コンテキストとコストの扱い

| 問題 | 対策 |
|---|---|
| CLAUDE.md が肥大化する | 100行以内。手順や詳細は docs/ と Skills に移し、必要なときだけ読ませる |
| レビューの指示が常に載る | レビュー用スキルにし、レビューのスレッドでだけ読ませる |
| テストや lint の結果が会話を埋める | Hooks で実行し、失敗したときだけ要点を返す |
| 広い調査で会話が膨らむ | サブエージェントに任せて要約だけ受け取る。1依頼に1スレッド |
| ツール定義が常にトークンを使う | MCP サーバー・サブエージェント・スキルは、このリポジトリで使うものだけ登録する |
| 指摘メモが肥大化する | 計画時は関係する行だけ検索して読む。週1の整理で消す |
| 先頭部分が変わるとキャッシュが効かない | CLAUDE.md や設定は作業中に編集せず、週1の整理 PR にまとめる。日付など毎回変わる値を書かない |
| 途中でコンテキストを入れ替えると高くつく | セッションの途中でツールやスキルの構成を変えない。別の作業は新しいスレッドで |
